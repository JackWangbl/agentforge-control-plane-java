一、AgentScope 与控制面基础

高频Q1. 什么是 AgentScope？它解决什么问题？和 LangChain / AutoGen 怎么区分？

标准答：AgentScope 是面向 Agent 应用的开发框架（阿里系开源，有 Python / Java 等实现），核心是把「模型 + 提示词 + 工具 + 消息循环」收成可组合的 Agent 运行时，并强调可调试、可扩展的工程能力。

  • 相对 LangChain：LangChain 更偏链式编排与生态插件；AgentScope 更强调 Agent 本体（ReAct 循环、工具、消息结构）和运行时可观测。
  • 相对 AutoGen：AutoGen 强在多 Agent 对话协作范式；AgentScope 单 Agent ReAct 很完整，多 Agent 可自建或与上层控制面结合。

结合本项目：控制面不重写推理引擎，而是用 AgentScope Java 的 ReActAgent + OpenAIChatModel 跑一轮对话；Agent 配置、权限、MCP、知识库、多智能体画布由 Spring Boot 控制面托管。

高频Q2. 你们项目里 AgentScope 处在哪一层？控制面又负责什么？

标准答：分层清楚：

层职责本项目对应
控制面租户、权限、Agent/模型/MCP/知识库 CRUD、编排发布、会话审计Spring Boot API + 静态控制台
运行时单轮对话、工具调用、ReAct 迭代AgentScopeRuntime
工具执行MCP / 沙箱 / 知识检索 / Flow / SubAgentToolRuntime + Overlay
编排多 Agent 路由、主从、流水线MultiAgentDebugService

面试加分句：「模型推理交给 AgentScope，业务治理留在控制面，避免把租户权限塞进框架内核。」

概念Q3. AgentScope 里一次对话的最小闭环是什么？

标准答：典型闭环是：

  1. 构造系统提示（角色 + 技能 + 工具说明）
  2. 把历史消息转成框架 Msg
  3. ReActAgent.call：模型思考 → 可能发起 ToolUse → 执行工具 → ToolResult 回填 → 再思考，直到给出最终回复或达到 maxIters
  4. 收集 usage、traces，写回会话/检查点

本项目：playground.generate → AgentScopeRuntime.generate → react.call(msgs, RuntimeContext)，超时约 5 分钟；浏览器类工具时 maxIters 提到 8，否则默认 4。

二、ReAct、工具与 Toolkit

必问Q4. 解释 ReAct。为什么 Agent 常用 ReAct 而不是一次 function call？

标准答：ReAct = Reason + Act：模型交替进行推理与行动（工具调用），根据观察再推理，直到任务完成。

一次 function call 适合「单次查数/单次动作」；复杂任务需要多步工具、根据中间结果改计划，所以用 ReAct 循环。代价是延迟和 token 更高，要用 maxIters、超时、权限和可观测兜住。

本项目：明确使用 ReActAgent.builder().maxIters(...).enablePendingToolRecovery(true)，并支持检查点续跑未完成的 tool。

必问Q5. Toolkit / Tool 在 AgentScope 里怎么工作？你们怎么挂动态工具？

标准答：Toolkit 是工具注册表。每个工具有名称、描述、JSON Schema 参数；模型通过 ToolUse 选择工具，框架回调执行，结果以 ToolResult 进入对话。

本项目落地：

  • 控制面先汇总 ToolSpec（MCP、内置、知识库、记忆、flow_ 链路等）
  • 用自定义 DelegatingTool 注册进 Toolkit，真正执行走 ToolRuntime.executeTool
  • 主从模式再通过 ToolOverlay 临时注入 call_sub_* SubAgent 工具，不写回 Agent 绑定

要点：「框架管协议与循环，控制面管鉴权与执行，」避免把租户逻辑写死在 AgentScope 里。

深挖Q6. 工具允许调用的权限怎么做？没绑工具时模型还调会怎样？

标准答：注册进 Toolkit 不等于业务允许。本项目在执行前调用 agentAllowsTool：按 Agent 绑定的 MCP/沙箱/知识库/flow/记忆工具白名单判断。未允许则返回错误 JSON（「Agent 未绑定工具 xxx」），并在 span 里记 error。

Overlay 的 SubAgent 工具走单独 executor，视为编排注入，不依赖 Agent 永久绑定。

深挖Q7. 什么是 Tool Flow？和多智能体 pipeline 有何不同？

标准答：

Agent 上的 tool_flows编排 pipeline
粒度单个 Agent 内部多个 Agent 节点
暴露方式模型看到一个 flow_xxx 工具图上串行/分支执行
执行FlowRuntime 按步骤调工具，步骤间可用 {{prev}} 引用每步是一次完整 Agent 生成

面试句：「Flow 是 deterministic 工具链；Pipeline 是多专家流水线。」

工程Q8. 没有 API Key 时你们怎么表现？

标准答：凭证为空时不调用真实模型，走预览回复 previewReply，并可演示部分本地工具（如时间）。这样控制台仍可演示 Agent 配置，但 mode 会标 preview/error，避免假装成线上可用。

三、记忆、会话与可观测

高频Q9. Agent 的短期记忆和长期记忆一般怎么设计？本项目呢？

标准答（通用）：短期=当前会话上下文；长期=跨会话可检索的事实/偏好。常用：滑动窗口、摘要、向量检索、显式 remember/forget 工具。

本项目：

  • 短期：MemoryService.shortTermHistory，多智能体调试时传 agentId=null 以共享会话内多节点历史
  • 长期：对话结束后 MemorySummarizer 总结；工具侧有 remember/forget/list_memories
  • 按用户/租户隔离，控制台可改正删除
高频Q10. RuntimeContext / sessionId 有什么用？

标准答：给运行时提供 userId、sessionId 等上下文，用于工作空间、检查点、追踪关联。本项目 RuntimeContext.builder().userId("playground").sessionId(...)；编排里主会话用 orch_*，SubAgent / pipeline 步用后缀隔离（如 ::sub::、::pipe::），防止子轮次污染主会话检查点。

高频Q11. 如何调试 Agent「到底调了什么工具」？

标准答：需要结构化 traces/spans：每步名称、类型（llm/tool）、耗时、截断后的 detail。本项目在 Toolkit 回调里写 debugSpan，flow 还有逐步 span；多智能体额外有 route.jump / route.handoff / route.supervisor / pipeline.step / subagent.*。控制台调试台与编排调试面板展示链路；生产 invoke 可剥掉 route 细节。

概念Q12. 系统提示词应该写什么？如何避免「改提示词写脏数据库」？

标准答：系统提示=角色、边界、输出格式、安全约束；工具说明可由框架/Toolkit 补充。动态叠加（全局人设、节点提示）不要直接改 JPA 实体字段。

本项目：PromptOverlay 用 ThreadLocal 前缀/后缀，仅本轮生效：global_prompt + 原系统提示 + 节点/主从说明，避免 OpenEntityManagerInView 下脏写回 Agent 表。

四、多智能体编排（本项目重点）

必问Q13. 移交（handoff）和主从（supervisor）有什么区别？
场景移交 handoff主从 supervisor
用户对面被选中的智能体始终是主智能体
下游角色接班人（换人聊）SubAgent 工具（干活交回）
单轮形态最多路由一次 + 一人回答主 ReAct 可多次 call_sub_*
像什么扣子多 Agent 场景跳转Supervisor + tools
必问Q14. 移交是靠什么移交的？只有一个意图识别吗？

标准答：不是只有一个意图识别。 本项目是两级、有优先级：

  1. 全局跳转（优先）：路由模型判断用户原话是否命中某条 jump 条件（如「转人工」）。命中则直接落到目标，不再做场景选择。
  2. 适用场景移交：未跳中时，在候选人（开始的出边，或当前节点的下游）里按「适用场景」文本做 LLM 分类；从 agent 出发时还允许「留下」(choice=-1)。

实现上是 temperature=0 的短 JSON 分类（{"choice":n}），不是独立训练的意图模型，也不是纯关键词。无可用路由模型时跳过跳转并按 fallback 规则处理（例如 start 多候选人失败时用第一个）。

高频Q15. 三种 pattern 分别什么时候用？
  • handoff：客服分流、专家切换，用户需要感觉「换人」。
  • supervisor：一个总入口汇总，需要调用多个专项能力（行程+预算）。
  • pipeline：固定步骤且有中间产物（素材→文案→校对）。

不要用 handoff 硬做强顺序流水线；不要用 pipeline 做闲聊分流。

深挖Q16. SubAgent 如何注入？如何防止递归互调？

标准答：开始节点只连一个主 Agent；主的出边变成 call_sub_<nodeId> 工具，描述来自适用场景，参数为 task。通过 ToolOverlay.call 注入本轮 Toolkit。

子 Agent 执行时用 ToolOverlay.nest 提高深度，使 current() 为空，子轮次看不到 SubAgent 工具，避免 A 调 B、B 再调 A。HTTP 智能体不走 AgentScope Toolkit，故不能作为挂 SubAgent 的主智能体。

深挖Q17. pipeline 如何传状态、防环？

第 1 步吃用户原话；后续步拼「用户原话 + 上一步输出」。多出边时复用 choice 分类做分支。用 visited 防环，MAX_PIPELINE_STEPS=8。每步独立临时 session，整链只对用户会话 finalize 一次，落点为最后一步。

工程Q18. 发布校验为什么重要？草稿能否调试？

发布时 requirePublishable：一 start、边类型、agent 可见且不重复、跳转条件与目标、pattern 专属规则（主从 start 只能连一个主、子要有 scenario 等）。保证线上图可运行。

当前实现：debug/invoke 要求 published；草稿可脏便于边画边存。这是体验与安全的折中；演进可做「带警告的试运行」。

场景Q19. dispatch=start 和 last 有什么差别？

会话持久化 current_node_id。start：每轮从开始节点重新分发；last：从上次落地 agent 继续，适合多轮粘在同一专家。主从多数时间落在主节点；pipeline 记录链尾节点。

五、工程化与对比题

高频Q20. Agent 幻觉调错工具、死循环怎么治理？
  • 工具描述写清适用边界；场景/跳转文案可区分
  • maxIters、超时、pending tool recovery / 检查点
  • 白名单 agentAllowsTool
  • 可观测 spans，线上按 route.detail 排查
  • 编排侧限制一跳、跳转条数、pipeline 步数与防环
对比Q21. 为什么不把多智能体也全塞进 AgentScope 原生多 Agent API？

标准答：控制面需要租户权限、发布校验、画布持久化、HTTP 智能体混布、与现有 playground/记忆体系统一。用图 JSON + 自研路由/主从/流水线，AgentScope 专注单节点 ReAct，边界清晰、可替换模型运行时。若团队强依赖框架原生多 Agent 协议，再评估迁移成本。
