# 知识库设计方案（第二版）

状态：已按此实现。

第一版已经落地：文档清洗、自动分块、Milvus 混合检索、分块只放在向量库。那些流水线保留。这一版改的是对象怎么划分、谁能看见、检索时权限怎么生效。

## 1. 现在别扭在哪

1. 建一个知识库之前，用户要先登记 Milvus 地址，再登记一个「重排序服务」。这是运维连接，不是业务对象。Dify、FastGPT、Bedrock Knowledge Base 都把向量库放在部署配置里，用户只创建知识库并选择模型和检索方式。
2. 重排序被做成和向量库并列的一种「库」。它是模型：有地址、模型名、密钥，调用一次给候选打分。和现有「模型配置」是同一类东西。
3. 创建时写入了 `owner_id`，列表和详情却只看租户。同租户里只要有 `knowledge:read`，就能看到别人的库、文档和检索结果。记了所有者，却没有所有者语义。
4. Agent 一旦绑了知识库，任何能和这个 Agent 对话的人都会搜到这些文档。权限只挡了管理页，没有挡检索。私人笔记绑到公共 Agent 上就会漏给别人。
5. 检索直接把小分块交给模型。小块适合命中，不适合回答。主流做法是用小块检索，把所在章节交回去。

## 2. 参照

| 产品或做法 | 采纳的部分 |
| --- | --- |
| Dify 的 Dataset | 知识库是用户对象。检索模式可选混合。重排序是可选模型。向量库是工作空间的基础设施 |
| RAGFlow | 按文档形态决定解析和分块，选择理由对用户可见，允许改策略后重建 |
| FastGPT | 默认只有创建者和被分享的人能用；团队公开是显式开关 |
| 企业 Copilot（Glean、Microsoft 365 Copilot） | 检索时再鉴权：Agent 绑定的范围和当前用户能看的范围取交集。权限变更不需要重建向量 |
| LlamaIndex 父子块、Dify 父子分段 | 子块做向量和关键词，父块（所在章节）作为返回给模型的上下文 |

不采纳的部分：文档级权限（同一库里不同人看不同文件）、知识图谱、OCR、网页同步。需要「一部分人只能看其中几份」时，拆成两个知识库。

## 3. 三层对象

```text
平台设置（租户管理员）
  默认 Milvus 连接
  模型：对话 / 向量 / 重排序
        │
        ▼
知识库（业务对象，默认私有）
  名称、可见性、成员、向量模型、可选重排序模型、检索条数
        │
        ▼
文档
  原始文件在磁盘，状态和策略在 MySQL，分块与向量只在 Milvus
```

用户路径变成：选向量模型，上传文件。不选 Milvus，不登记重排序「库」。

### 3.1 平台基础设施

向量库连接保留 `vector_stores`，从知识库向导里拿掉，只出现在平台设置，并且只有租户管理员能改。每个租户有一个默认连接。知识库创建时抄下这个连接的 id，之后检索和入库都用它。管理员更换默认连接，不影响已经建好的库；要换某库的连接，走「重建索引」。

重排序不再使用 `rerank_stores`。`model_configs.purpose` 增加 `rerank`，与 `chat`、`embedding` 并列。字段沿用模型配置已有的名称、地址、模型名、密钥。知识库上的 `rerank_store_id` 改为可空的 `rerank_model_id`。不选则混合检索的 RRF 名次直接截断。选了但调用失败，这次检索失败，不悄悄退回 RRF。

调用协议保持现在的 `POST {base_url}/rerank`。

### 3.2 知识库

在现有 `knowledge_bases` 上增加可见性，成员单独一张表。

| 列 | 说明 |
| --- | --- |
| `visibility` | `private` 或 `tenant`。新建默认 `private` |
| `embedding_model_id` | 仍必填，必须是 `purpose=embedding` |
| `rerank_model_id` | 可空，必须是 `purpose=rerank` |
| `vector_store_id` | 创建时写入租户默认连接，界面不让普通用户改 |
| `top_k`、`candidate_k`、`score_threshold` | 含义与第一版相同。阈值只在选了重排序模型时生效 |

`knowledge_members`：

| 列 | 说明 |
| --- | --- |
| `knowledge_id` | 所属知识库 |
| `user_id` | 同租户用户 |
| `role` | `owner`、`editor`、`viewer` |

创建者自动成为 `owner`。同一库、同一用户只有一条。`visibility=tenant` 不给表里插全员记录，读的时候按可见性展开。

角色能做的事：

| 动作 | owner | editor | viewer | 租户管理员 |
| --- | --- | --- | --- | --- |
| 查看库、文档、调试检索 | 能 | 能 | 能 | 管理界面能看全部 |
| 上传、删除文档、改分块策略、重建 | 能 | 能 | 不能 | 不能凭管理员身份改别人的库 |
| 改名称、模型、检索参数、可见性 | 能 | 不能 | 不能 | 不能 |
| 添加和移除成员、删除知识库 | 能 | 不能 | 不能 | 不能 |

租户管理员在管理界面看得到全部知识库，用来排障。管理员身份不自动变成 owner，也不能借这个身份检索别人的私有文档。

可见性：

- `private`：只有成员能看见。直接用 id 访问，非成员得到「不存在」，不提示这个库属于谁。
- `tenant`：同租户里拥有 `knowledge:read` 的人都能查看和检索，权限等同 viewer。上传和修改仍要成员角色。

`knowledge:read` / `knowledge:write` 继续作为进门权限。没有 `knowledge:read` 的角色，列表是空的，也不能被加为成员后看到内容。没有 `knowledge:write` 的人，即使是成员也不能上传。

### 3.3 文档和父子块

上传、清洗、自动选择分块策略、原始文件放 `rag-files/`、分块正文不进 MySQL，这些保持第一版。

每个子块在 Milvus 里多一个上下文字段：

| 字段 | 用途 |
| --- | --- |
| `content` | 子块原文。稠密向量和 BM25 都用它 |
| `context` | 交给模型的章节。标题路径加上该标题下的正文，最长 2000 字。预览也能看到它 |
| `heading` | 标题路径，已有 |

子块仍按第一版的长度切（中文目标 450、重叠 60；英文 1000、120）。`context` 是同一标题下相邻子块拼起来的章节，不是另一套向量。没有标题时，`context` 就是该子块本身。

权限不写进向量。分享或改成租户可见之后立刻生效，不用重建。检索过滤用本次请求算出来的知识库 id 列表。

## 4. 检索时的权限

对话时的检索范围是两个集合的交集：

1. 这个 Agent 绑定的、已启用的知识库。
2. 当前登录用户能看见的知识库（成员，或 `visibility=tenant` 且有 `knowledge:read`）。

只在这些库的就绪文档、当前代次上做混合检索。结果按知识库各自的重排序和阈值处理，再合并成至多 `top_k` 条。返回给模型的是 `context`、文件名和标题，不是孤立的半句话。

交集为空时，工具返回「当前没有你可以检索的文档」。不列出被绑上但你看不见的库名。

因此：

- 私人笔记保持 `private`。即使绑到公共 Agent，也只有成员能搜到。
- 全员制度设为 `tenant` 再绑定，所有有读权限的对话者都能搜到。
- 用户 A 不能通过猜 id、调试检索或别人的 Agent，读到用户 B 的私有库。

保存 Agent 时，操作者必须至少能看见每一个要绑定的库。HTTP Agent 仍然不能绑定知识库。

## 5. 界面

知识库页只保留业务对象：

- 列表分组：我创建的、分享给我的、租户公开。
- 新建：名称、说明、向量模型、可见性。高级项是重排序模型、返回条数、候选数、分数阈值。
- 库内：成员、上传、清洗摘要、分块策略和理由、章节预览、调试检索。
- Milvus 连接挪到平台设置，入口只给租户管理员。

模型配置的用途下拉增加「重排序」。重排序模型不出现在对话模型里。

## 6. 和第一版的对应

| 第一版 | 第二版 |
| --- | --- |
| 每个知识库必选 Milvus 连接 | 租户一个默认连接，创建时写入，普通用户不可选 |
| `rerank_stores` | 取消。改用 `purpose=rerank` 的模型配置 |
| `owner_id` 只记录、列表按租户全开 | `visibility` + `knowledge_members`，默认私有 |
| Agent 绑定后谁对话谁都能搜 | 绑定范围与当前用户可见范围取交集 |
| 命中块直接返回 | 命中用子块，返回 `context` 章节 |
| 清洗、自动分块、混合检索、原文在磁盘、分块只在 Milvus | 保留 |

已有数据的迁法，批准后再做：现有库视为 `visibility=tenant`，创建者补一条 `owner` 成员，避免突然从共享变成只有一个人能看见。没有默认 Milvus 时，沿用该库已经保存的 `vector_store_id`。

## 7. 验收

- 用户 A 新建库，默认只有 A 能在列表、详情和调试检索里看到。用户 B 用 id 访问，得到不存在。
- A 把 B 加为 viewer，B 能看不能上传。加为 editor 后 B 能上传。
- 库改成租户公开后，同租户有 `knowledge:read` 的人能看能搜，不能上传。
- 公共 Agent 绑了 A 的私有库。B 与该 Agent 对话时检索不到其中文档，响应里也没有这个库的名字。
- 新建知识库的表单没有 Milvus 地址，也没有「重排序数据库」。
- 调试检索的一条结果同时有命中的子块和更长的章节上下文。
