# Feature Specification: 失败 Case 检查点重拾

**Feature Branch**: `main` (spec-only; no feature branch created)

**Created**: 2026-10-27

**Status**: Draft

**Input**: User description: "分析当前项目请求链路，参照 LangChain checkpoint 原理，增加失败重拾功能，支持从失败处使用原请求入参继续执行；增加失败 Case 模块，展示失败率、请求入口、请求 Agent、原入参和失败原因；重拾成功后不可再次重拾。"

## Current-State Analysis & Scope

当前项目已有请求入口、会话、执行链路和 Agent 工作空间等基础能力。Agent 调试台能在部分执行失败时保留当前状态并继续执行，但该能力仍依附于单个调试会话，尚未形成面向运维和排障的统一失败 Case 管理能力。当前还缺少统一的失败统计口径、请求入口识别、原始入参快照、重拾尝试记录和成功后的终态保护。

本功能将现有的执行恢复能力扩展为统一的“失败 Case”模块，纳入当前项目中的 Agent 调试台、Agent 直接调用、工作流调试/调用和 A2A 调用入口。一个请求在通过基本校验并进入 Agent 执行后，如因模型、工具、子 Agent、外部 Agent、路由或工作流节点异常而未正常完成，则生成失败 Case。鉴权失败、请求格式错误等未进入执行链路的请求不在本期失败 Case 范围内。

“重拾”采用检查点的行为语义：系统在可恢复的执行边界保留状态快照；重拾时使用不可编辑的原请求入参和原执行上下文，从最后一个已确认成功步骤之后继续。已确认成功的步骤不得因重拾被重复执行。

## Clarifications

### Session 2026-10-27

- Q: 当工具或外部系统可能已经产生副作用、但平台无法确认结果时，是否允许用户强制重拾该步骤？ → A: 默认禁止无幂等保障的重拾；管理员明确确认风险后可例外强制重拾，并完整记录审计信息。
- Q: 用户发起重拾后，页面请求应等待执行完成，还是立即返回并由后台继续执行？ → A: 采用混合执行：短任务在请求内等待，超过明确阈值后无缝转为后台任务。
- Q: 重拾的同步等待、单步骤执行和整次重拾应采用哪套超时规则？ → A: 同步等待 3 秒、单步骤默认 5 分钟、整次重拾默认 30 分钟；管理员可在平台允许范围内按 Agent 或工作流覆盖，任务启动时固化当次超时值。
- Q: 重拾时，Agent、模型参数、工具及工作流应使用失败发生时的配置版本，还是重拾时的最新配置？ → A: 使用失败时固化的逻辑配置版本；凭证仅保存安全引用并在重拾时读取当前有效值。
- Q: 多个不同 Failure Case 同时重拾时，应采用哪种并发与排队上限？ → A: 默认每个 Agent 同时 2 个、每个租户同时 10 个重拾任务，每租户最多排队 100 个；管理员可在平台安全上限内调整，队列满时明确拒绝且不创建重拾尝试。
- Q: 重拾（重试）成功后，用户为什么在「会话查询」里看不到记录？应如何处理？ → A: 这是缺陷，不是预期。会话查询只展示平台会话事实（会话、消息、可审计链路），不展示仅写在失败 Case、重拾尝试或调试工作区里的结果。重拾成功必须把同一会话标识下的对话写入会话查询；原失败若尚未创建会话，成功时必须补建。不得另开一条无关会话作为唯一成功记录。未写入会话查询的成功不得视为完整成功。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查看和定位失败 Case (Priority: P1)

具有运行查看权限的用户进入“失败 Case”模块，可看到租户范围内的失败率和失败列表，并按时间、请求入口、Agent、状态筛选。用户可从列表中直接识别失败的请求来源、目标 Agent、失败时间、失败步骤和是否可重拾。

**Why this priority**: 只有先为失败执行建立统一、可检索的事实视图，用户才能可靠地定位问题和判断是否重拾。

**Independent Test**: 构造不同入口和 Agent 的成功与失败执行，验证失败率、列表字段、筛选结果和租户隔离是否与执行事实一致。

**Acceptance Scenarios**:

1. **Given** 选定时间范围内有 80 次成功和 20 次失败的已结束执行，**When** 用户打开失败 Case 模块，**Then** 页面显示 20.0% 失败率和 20 个失败 Case，运行中请求不进入分子或分母。
2. **Given** 失败 Case 来自调试台、Agent 直接调用、工作流调用和 A2A，**When** 用户按入口或 Agent 筛选，**Then** 仅显示匹配的 Case，每条都显示准确的入口、Agent 和发生时间。
3. **Given** 用户尝试查看其他租户的 Case 或无权资源，**When** 用户访问列表或详情，**Then** 系统不显示该 Case 及其任何入参、原因或执行信息。

---

### User Story 2 - 审查原入参与失败原因 (Priority: P1)

用户打开失败 Case 详情，查看重拾前的原始请求入参、失败类别、失败步骤、可读错误摘要、发生时间及截至失败点的执行步骤。

**Why this priority**: 重拾前必须让用户确认重现条件和失败位置，避免盲目重试或泄露敏感信息。

**Independent Test**: 使用包含普通字段和敏感字段的失败请求，验证有权用户可看到不可编辑的原入参和可用的失败诊断，同时敏感值按平台规则遮罩。

**Acceptance Scenarios**:

1. **Given** 一个可重拾的失败 Case，**When** 用户打开详情，**Then** 系统显示当初接收的完整请求结构、入口、目标 Agent、失败步骤、失败类别和错误摘要，且入参不可编辑。
2. **Given** 原入参或失败信息包含凭证、令牌或已配置为敏感的字段，**When** 用户查看详情，**Then** 敏感值被遮罩，不在列表、详情、导出内容或错误文本中明文显示。
3. **Given** 一个 Case 经历多次重拾失败，**When** 用户查看详情，**Then** 可看到每次尝试的时间、结果、失败步骤和原因，同时原始请求入参保持不变。

---

### User Story 3 - 从失败点重拾执行 (Priority: P1)

具有重拾权限的用户在 Case 详情中发起重拾。系统必须使用创建 Case 时保存的原入参和执行上下文，从最近的可恢复失败点继续，而不是从请求起点重新运行。

**Why this priority**: 这是功能的核心价值，可避免重复模型消耗、重复工具副作用和人工重放整条链路。

**Independent Test**: 在多步执行的中间步骤注入一次性失败，确认重拾使用原入参，跳过已成功步骤，仅从失败/未完成步骤继续，并产生完整的重拾记录。

**Acceptance Scenarios**:

1. **Given** 一条执行在第 3 步失败且第 1、2 步已确认成功，**When** 用户发起重拾，**Then** 系统从第 3 步继续，不再执行第 1、2 步，并使用与原 Case 一致的请求入参。
2. **Given** 原执行已成功完成一个带副作用的工具步骤，之后在模型步骤失败，**When** 用户重拾，**Then** 已完成的工具步骤不被重复调用。
3. **Given** 同一 Case 已有一次重拾正在执行，**When** 另一个用户或重复操作再次发起重拾，**Then** 系统拒绝重复执行并显示当前正在重拾。
4. **Given** 原 Agent 配置版本、执行上下文或凭证引用已不可用，**When** 用户发起重拾，**Then** 系统不开始不完整的执行，不自动改用最新配置，说明不可执行的原因，并保留 Case 及已有检查点。
5. **Given** 重拾未在同步等待阈值内完成，**When** 请求达到该阈值，**Then** 系统返回可查询的重拾任务标识并在后台继续原执行，不取消、重启或重复当前步骤。
6. **Given** 某租户的重拾队列已达上限，**When** 用户再发起重拾，**Then** 系统明确告知繁忙和可重试时机，不创建重拾尝试，不改变 Case 状态。

---

### User Story 4 - 关闭已成功重拾的 Case (Priority: P2)

当重拾完成整条请求后，Case 进入“重拾成功”终态，保留原失败记录和重拾结果供审计，但不再允许任何用户对该 Case 发起重拾。

**Why this priority**: 终态保护能避免重复产生输出、重复调用外部服务和破坏审计语义。

**Independent Test**: 令一个 Case 重拾成功，再通过页面及直接请求重复发起重拾，验证入口均不再可用且原/新执行记录保持完整。

**Acceptance Scenarios**:

1. **Given** 某 Case 重拾成功，**When** 用户回到列表或详情，**Then** 状态显示为“重拾成功”，重拾操作不再可用，页面可查看成功尝试的时间和关联结果。
2. **Given** 已重拾成功的 Case，**When** 任何用户尝试绕过页面再次发起重拾，**Then** 系统拒绝请求，不创建新尝试，不改变已完成结果。
3. **Given** 一次重拾再次失败，**When** 执行结束，**Then** Case 保持可重拾，检查点更新到本次失败处，直到某次重拾成功才进入终态。

---

### User Story 5 - 重拾成功后在会话查询中核对结果 (Priority: P1)

具有会话查看权限的用户在失败 Case 重拾成功后，进入现有「会话查询」模块，必须能按原会话标识找到这一次对话，打开详情后看到原用户入参、重拾完成后的助手回复，以及可审计的执行链路。用户不必回到失败 Case 或调试台工作区才能确认“这次重试到底说了什么”。

**Why this priority**: 运维和排障的日常核对入口是会话查询，不是 Failure Case。若重拾只更新 Case 状态或调试工作区，用户会误以为重试没有发生。

**Independent Test**: 从调试台、Agent 直接调用等入口构造一次可恢复失败并完成重拾；不打开失败 Case，只在会话查询中按原会话标识检索并打开详情，确认会话、消息和链路均可见。

**Acceptance Scenarios**:

1. **Given** 一次原始请求已失败且随后重拾成功，**When** 有权用户打开「会话查询」并用原会话标识检索，**Then** 恰好出现一条该会话记录，Agent、用户和更新时间与这次重拾一致，状态为已完成。
2. **Given** 原失败发生在会话记录尚未创建之前（例如调试台首轮失败，页面尚未落会话），**When** 重拾成功，**Then** 会话查询中仍能看到该会话；系统必须补建会话和消息，而不是因为原失败未落库就继续缺失。
3. **Given** 用户打开该会话详情，**When** 查看消息和链路，**Then** 至少包含原始用户入参和重拾完成后的助手回复，并有一条可打开的执行链路；不得只有空白会话或只有失败 Case 里的摘要。
4. **Given** 重拾已在失败 Case 中显示成功，但会话查询按原会话标识找不到记录或缺少助手回复，**When** 验收该次重拾，**Then** 该次不得被判定为完整成功，必须视为会话落库失败并保留可重拾或转人工，不得静默只改 Case 状态。

### Edge Cases

- 请求在任何可恢复步骤开始前失败时，Case 必须显示为不可重拾，同时保留失败原因供排障。
- 服务在步骤实际完成后、成功状态确认前中断时，该步骤必须被视为“结果未确认”；若无法证明重复执行安全，默认禁止重拾并显示人工处理提示，仅允许管理员在明确确认风险后例外强制重拾。
- 重拾期间 Agent 被禁用、删除，或其依赖不可用时，必须拒绝开始或安全地终止，且 Case 不得误标为重拾成功。
- 失败后管理员修改了 Agent、模型参数、工具或工作流配置时，已存在 Case 的重拾仍使用失败时的逻辑配置版本；如该版本不可用，必须转人工处理，不得静默使用最新版本。
- 单步骤或整次重拾超时时，系统必须尝试安全终止未完成工作，将超时记录为本次失败原因，并仅在存在已确认的安全检查点时保留可重拾状态。
- 原始入参过大或包含不支持的二进制内容时，系统必须明确记录可重拾的引用或标记为不可重拾，不得静默丢失入参。
- 同一会话内有多次失败执行时，每次执行必须有独立 Case，重拾一个 Case 不得改写其他 Case 的状态。
- 重拾结果已成功但用户未收到响应时，重新加载页面必须显示服务端已确认的终态，不允许用户因响应丢失而重复重拾。
- 统计时间边界、分页和筛选组合必须使用同一时区和相同的失败口径，避免指标与列表不一致。
- 后台重拾执行器突然中断时，系统必须依据持久状态识别“仍在运行”的过期任务，不得将其永久留在运行中；只能从已确认安全检查点恢复，无法确认时转人工处理。
- 重拾成功后用户在「会话查询」看不到记录时，不得解释为“重拾只存在于失败 Case 模块”。该现象表示会话事实未写入会话查询所依赖的平台会话记录。
- 原请求失败时若尚未创建会话或消息，重拾成功必须按原会话标识补建，不得因“失败时没有会话”而继续在会话查询中缺失。
- 重拾必须复用原会话标识，不得为了写入会话查询而另开一条无关会话，导致用户按原会话标识仍查不到。
- 仅更新调试工作区、检查点或 Failure Case，而不同步会话、消息和可审计链路时，用户在会话查询中必然看不到这次重试；这不满足本功能。
- 重拾再次失败时，不得把未完成回复写成一条成功会话；会话查询中的会话状态不得因此被误标为已完成成功。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供独立的“失败 Case”模块，展示用户有权访问的执行失败记录。
- **FR-002**: 系统必须在请求通过基本校验并进入 Agent 执行链路后为每次执行分配唯一标识，并保留其入口、目标 Agent、会话/关联链路、开始时间、结束时间和最终状态。
- **FR-003**: 系统必须将调试台、Agent 直接调用、工作流调试、工作流调用和 A2A 作为可识别的请求入口，列表和详情中必须使用统一的可读名称展示。
- **FR-004**: 系统必须将失败率定义为“选定时间和筛选范围内的失败原始执行数 ÷ 已结束原始执行总数”；重拾尝试不重复计入原始请求失败率，运行中请求不进入分子或分母。
- **FR-005**: 失败 Case 页面必须默认显示最近 24 小时，并支持至少按时间范围、请求入口、请求 Agent 和 Case 状态筛选；指标与列表必须同步使用当前筛选条件。
- **FR-006**: 每个失败 Case 必须保留不可变更的原始请求入参快照，包括用户提交的业务入参以及继续执行所需的会话和入口上下文。
- **FR-007**: 页面必须允许有权用户在重拾前查看原始入参快照，但不得允许对快照进行编辑或替换。
- **FR-008**: 系统必须在展示、记录和导出原入参与失败原因时遮罩密码、API Key、令牌、授权信息及其他被标识为敏感的字段。
- **FR-009**: 系统必须为每个失败 Case 记录失败类别、失败步骤、可读错误摘要、发生时间和已完成的执行步骤；有诊断权限的用户还应能查看不含敏感值的详细错误信息。
- **FR-010**: 系统必须在每个可恢复执行边界保留足以重建执行状态的检查点，至少能区分已确认成功、失败、未开始和结果未确认的步骤。
- **FR-011**: 重拾必须使用原始入参快照和原执行上下文，并在开始前验证它们未被替换或篡改；验证不通过时不得执行。
- **FR-012**: 重拾必须从最近的可恢复失败/未完成步骤继续，已确认成功的步骤不得被重复执行。
- **FR-013**: 对结果未确认且可能产生副作用的步骤，系统必须默认禁止重复执行，并将 Case 标记为需要人工处理。仅管理员可在提交强制理由、明确确认重复副作用风险后发起例外强制重拾；系统必须记录管理员、理由、确认时间、风险类型和执行结果。
- **FR-014**: 系统必须确保同一 Case 在同一时间最多只有一次重拾执行，并拒绝重复点击或并发请求。
- **FR-015**: 每次重拾尝试必须记录发起人、发起时间、起始检查点、结束时间、结果、新的失败原因或成功结果关联，且不得覆盖原失败记录。
- **FR-016**: 重拾再次失败时，系统必须保留 Case 的可重拾状态并更新到最新可恢复检查点，同时完整保留历次尝试。
- **FR-017**: 重拾成功时，系统必须以不可逆的业务状态将 Case 标记为“重拾成功”，关联最终执行结果，并在页面和所有请求入口永久拒绝对该 Case 的再次重拾。标记“重拾成功”的前提是 FR-028 至 FR-031 的会话查询事实已写入；会话落库失败时不得将 Case 标为重拾成功。
- **FR-018**: Case 状态至少必须区分“可重拾”、“重拾中”、“需人工处理”和“重拾成功”，并为每个状态提供明确的可用操作。
- **FR-019**: 只有拥有对应租户、Agent/工作流以及执行记录读权限的用户才能查看 Case；发起重拾还必须具有对应执行权限。
- **FR-020**: 失败 Case 列表、详情、指标和重拾结果必须在刷新页面、会话切换或服务重启后保持一致，不能仅依赖用户当前浏览器状态。
- **FR-021**: 重拾必须采用混合执行模式：在可配置的短时同步等待阈值内完成时直接返回结果；超过阈值时必须返回可查询的任务标识并在后台继续同一次重拾。转入后台不得取消、重启或重复当前执行步骤，也不得长时间占用原请求处理线程。
- **FR-022**: 重拾的同步等待阈值默认为 3 秒，单步骤超时默认为 5 分钟，整次重拾超时默认为 30 分钟。管理员可在平台允许范围内按 Agent 或工作流覆盖这些值；每次重拾必须在任务启动时固化其实际超时值，运行期间的配置修改不得影响已启动任务。
- **FR-023**: 单步骤或整次重拾超时必须被记录为明确的失败类别和尝试结果。系统必须尝试安全终止未完成工作；仅当存在已确认的安全检查点时，Case 才可继续保持“可重拾”，否则必须转为“需人工处理”。
- **FR-024**: 系统必须在原执行开始时固化重拾所需的 Agent、模型参数、工具和工作流逻辑配置版本。重拾必须使用该版本，不得因后续配置变更而改变执行语义。密码、API Key 和令牌不得复制进配置快照，只能保存安全凭证引用并在重拾时解析当前有效值。原配置版本或凭证引用不可用时，不得自动降级或切换到最新配置。
- **FR-025**: 系统必须对不同 Case 的重拾执行实施分层并发与排队限制：默认每个 Agent 最多同时运行 2 个重拾任务，每个租户最多同时运行 10 个，每个租户最多排队 100 个。管理员可在平台安全上限内调整；已启动任务的并发配置在运行期间不变。队列已满时必须拒绝新请求，不创建重拾尝试且不改变 Case 状态。
- **FR-026**: 系统必须将重拾异常至少分为超时、上游/外部依赖失败、模型失败、工具失败、配置或凭证不可用、权限变更、输入/检查点完整性失败、并发冲突和未知内部错误。所有异常必须结束或转移重拾任务状态、保留最后已确认的安全检查点，并向用户返回可读且不含敏感信息的错误摘要；不得静默吞掉异常或将失败标记为成功。
- **FR-027**: 重拾日志必须默认只记录租户、Case、重拾尝试、任务、链路、Agent/工作流、步骤、异常类别、状态变化、耗时和脱敏错误摘要等关联信息。日志不得记录原始请求入参、完整模型输入/输出、凭证明文、未脱敏工具参数/结果或可能含敏感数据的原始异常文本。详细诊断必须受诊断权限和租户隔离约束，且在持久化前执行脱敏。
- **FR-028**: 重拾成功后，拥有会话查看权限的用户必须能在现有「会话查询」中按原会话标识检索到该次对话。会话查询是平台会话事实的唯一人机核对入口；失败 Case 详情、重拾尝试记录和调试工作区投影都不能替代它。
- **FR-029**: 写入会话查询的必须是原请求使用的同一会话标识、同一租户和同一 Agent，并遵循现有会话可见性（租户隔离与会话读权限）。系统不得另开一条无关会话作为这次重拾的唯一可见记录。
- **FR-030**: 该会话详情必须包含原始用户入参和重拾完成后的助手回复，以及至少一条可从该会话打开的执行链路。原失败若尚未创建会话或消息，重拾成功时必须补建，不得继续缺失。
- **FR-031**: 系统必须把上述会话、消息和链路作为重拾成功提交的一部分。只更新 Failure Case 状态或只写入调试工作区时，该次重拾不得进入“重拾成功”终态；应保留可重拾或转为需人工处理，并向用户返回不含敏感信息的失败原因。

### Key Entities

- **Execution Record (执行记录)**: 一次已进入 Agent 执行链路的原始请求；包含唯一标识、租户、请求入口、目标 Agent/工作流、会话与链路关联、时间和最终状态。
- **Failure Case (失败 Case)**: 与一条失败原始执行一对一关联的可运维对象；包含原入参快照、失败分类、失败步骤、原因、可恢复性、当前状态和最终恢复结果。
- **Checkpoint (检查点)**: 执行边界上的持久状态快照；标识已确认成功的步骤、下一待执行步骤、中间状态和是否安全可恢复。
- **Recovery Attempt (重拾尝试)**: 用户针对一个 Failure Case 发起的一次继续执行；包含发起人、起始检查点、时间、结果、异常原因及关联的最终执行。
- **Recovery Task (重拾任务)**: 承载一次重拾尝试的可查询执行单元；在同步等待超时后继续运行，并持续反映排队、运行、成功、失败或超时状态。
- **Platform Session Record (平台会话记录)**: 「会话查询」所展示的会话、消息和可审计链路；与原请求的会话标识绑定。重拾成功必须更新或补建该记录，调试工作区中的会话文件不是会话查询的数据源。
- **Request Input Snapshot (请求入参快照)**: 失败执行开始时的不可编辑请求数据及必需上下文；与用于防篡改验证的恒定标识关联，展示时执行敏感信息遮罩。
- **Execution Configuration Snapshot (执行配置快照)**: 原执行所使用的 Agent、模型参数、工具和工作流逻辑版本；不包含凭证明文，只保留可在重拾时解析的安全引用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 对所有已纳入范围的失败执行，100% 能在 1 分钟内出现在失败 Case 列表中，并显示入口、Agent、时间、状态和失败摘要。
- **SC-002**: 在给定时间与筛选范围内，页面失败率与逐条执行事实计算结果一致，准确率为 100%。
- **SC-003**: 对于可恢复的注入失败用例，至少 95% 的重拾在无新故障时能从失败步骤继续并完成，且原请求入参逐字节保持一致。
- **SC-004**: 在全部重拾验收用例中，已确认成功的步骤重复执行次数为 0，同一 Case 的并发重拾次数为 0。
- **SC-005**: 已重拾成功的 Case 在页面、重复点击和直接请求三类验收中，再次执行次数为 0。
- **SC-006**: 有权用户能在 2 分钟内从失败列表定位一个指定 Case，查明请求入口、Agent、原入参和失败原因，并完成可重拾性判断。
- **SC-007**: 权限隔离和敏感信息验收用例全部通过：跨租户或无权数据暴露为 0，页面、记录和导出中的明文凭证暴露为 0。
- **SC-008**: 在服务重启、页面刷新和用户重新登录后，100% 的失败 Case、重拾状态和历次尝试仍可正确查看。
- **SC-009**: 在超时验收用例中，100% 的同步请求在 3 秒阈值后释放原请求处理线程，100% 的单步骤和整体超时被准确记录，且不会将超时任务误标为成功。
- **SC-010**: 在并发压力验收中，任何 Agent 和租户的同时重拾数均不超过当时生效上限，租户排队数不超过上限，超额请求 100% 被明确拒绝且不产生幽灵尝试记录。
- **SC-011**: 异常与日志安全验收用例全部通过：所有注入异常均进入明确终止/人工处理状态并可通过关联标识排查；日志中的原始入参、完整模型内容、凭证明文和未脱敏异常文本暴露次数为 0。
- **SC-012**: 在全部重拾成功验收用例中，按原会话标识在「会话查询」中检索的命中率为 100%，且每条会话详情都包含重拾完成后的助手回复和可打开链路；成功重拾后会话查询不可见的次数为 0。

## Assumptions

- 本期面向已通过基本验证并进入 Agent 执行链路的请求；登录、鉴权、参数校验等执行前失败不生成 Failure Case。
- 第一期纳入项目当前的 Agent 调试台、Agent 直接调用、工作流调试/调用和 A2A 入口；评测任务本身的“续跑失败用例”属于现有独立能力，不与本模块合并。
- 默认统计时间范围为最近 24 小时，用户可切换到其他支持的时间范围。
- 重拾必须复用失败时已保存的请求入参、执行上下文和逻辑配置版本；用户不能通过重拾更换入参、Agent、模型参数、工具或工作流。如需使用新入参或新配置，应发起一次新请求。
- 重拾成功是 Failure Case 的终态；重拾失败不是终态，仍可从最新的安全检查点再次重拾。
- 失败详情和原入参沿用项目现有的租户隔离与资源权限模型，重拾操作要求与原入口等价的执行权限。
- 「会话查询」沿用现有会话查看能力与权限；本功能不新增第二个会话浏览器。重拾成功必须写入该模块已经在展示的会话事实。
- 失败 Case 和重拾尝试按平台通用运行审计保留策略存续；本期不提供单独的手工删除功能。

## Out of Scope

- 修改原始请求入参后再执行；这属于新请求，不是重拾。
- 自动无限重试、定时重试或按错误类型配置自动重试策略。
- 允许普通用户对结果未确认且无法证明幂等的外部副作用进行强制重放；管理员的审计例外按 FR-013 执行。
- 将评测模块已有的失败数据集用例续跑并入本模块。
- 设计或更换现有 Agent、模型、工具、工作流和 A2A 的业务配置。
